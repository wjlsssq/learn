# 架构约定

## 目标与边界

工作台承载逐步形成的学习工程：统一入口、独立实现、按需复用、文档持续维护。新增功能由学习链路驱动，先确定本次场景和验收方式，再选择工程结构。

当前基础阶段包含静态门户、基础服务及其公共能力。门户的工程登记信息不依赖后端或数据库。基础服务用于提供真实的运行信息、健康检查，并验证 Java Web 公共能力的接入。

登录权限、数据库、中间件、Agent 和工程生成器均不属于本阶段。具体交付状态和验证结果只记录在 [PROGRESS.md](PROGRESS.md)。

## 仓库组织

```text
portal/                           @learn/portal：工程导航、文档浏览
shared/frontend/http/             @learn/http：HTTP 基础机制
shared/frontend/ui/               @learn/ui：公共样式变量
shared/java/web-support/           Java Web 基础能力
projects/foundation-service/      独立 Spring Boot 应用
projects/<future-project>/        未来工程，各自选择内部结构
tooling/                          当前工程启动、构建与检查辅助
docs/                            仓库级规范、进度与决策
```

pnpm workspace 负责前端包管理；Maven 根 POM 聚合 Java 模块并管理依赖与插件版本。两者分别覆盖适合的工程，不要求 Python 工程加入 Maven 或所有工程都拥有前端。

## 依赖规则

允许的主要依赖方向：

```text
portal → shared/frontend
Java 工程 → shared/java
未来 Python 工程 → 实际需要时创建的 Python 公共库
```

公共库不依赖具体工程，独立工程不直接引用其他工程的内部实现。跨工程调用通过明确的接口或事件契约完成；只有存在真实协作需求时才建立这些连接。

公共模块承载技术机制，例如请求关联、异常映射、HTTP 传输和样式变量。业务实体、查询、持久化映射、状态机、Agent 工具和提示词归工程所有。先在具体场景验证，再评估复用价值。

## 门户

- 工程卡片来自门户维护的工程登记信息；新增工程按[接入指南](PROJECT_ONBOARDING.md)手动接入。
- 页面提供搜索、工程详情和真实文档入口。未接入的技术方向不展示为已经建成的工程。
- 初始运行状态为未检测；用户主动探测后展示检查中、在线或离线等结果。离线描述的是探测失败，不能单凭网络失败断言具体故障原因。
- 点击页面不会启动后端或中间件。进程由开发终端中的命令管理。
- 开发模式通过 `/foundation-api` 代理到基础服务，代理移除该前缀；门户静态生产产物需要部署环境提供对应反向代理，才能继续探测本地或部署后的服务。

## Java 基础能力

`web-support` 以普通依赖提供公共 Web 机制，应用通过 `@Import(WebSupportConfiguration.class)` 显式接入。它不负责应用启动、不扫描或接管业务包，也不引入数据库或中间件。

基础约定：

- 成功响应直接遵循接口契约，不做全局包装。
- 错误响应使用 `{ code, message, traceId, timestamp, path, violations? }`；错误类别保留对应 HTTP 状态。
- 参数校验返回可定位的校验信息；未知异常返回安全的通用描述，内部原因留在日志。
- 响应头 `X-Request-Id` 与错误体 `traceId`、日志 MDC 的 `traceId` 对齐。符合安全格式的来访标识可透传，否则生成新的标识。
- 业务工程维护自己的错误码与领域规则。HTTP 状态属于协议语义，业务错误码用于进一步区分原因。
- 文件下载和 SSE 等接口遵循自身协议，不强制套用 JSON 成功结构。

`foundation-service` 默认监听 `127.0.0.1:18080`。公开基础接口为：

| 接口                       | 内容                                  |
| -------------------------- | ------------------------------------- |
| `GET /api/foundation/info` | 服务名称、版本、Java 版本和已接入能力 |
| `GET /actuator/health`     | 运行健康状态                          |

接口中能力列表仅描述实际接入的基础功能，不代表数据库、中间件或未来学习模块已经具备。

## 后续工程的内部结构

Java 工程可以按业务模块组织接口、应用编排、业务规则和基础设施实现；根据业务复杂度确定包或构建模块边界。Python 工程遵循适合其框架的结构，仍需有明确的职责、配置、测试和启动说明。

一个 Agent 工程可以只有 Python 服务，也可以有 Vue 界面或 Java 协作服务。每个额外进程应有真实职责、明确契约和独立启动方式。

需要持久化时，为该工程建立数据模型和迁移脚本；需要 Redis、MQ 等资源时，声明命名、访问和隔离方式。性能或故障实验使用不会干扰其他工程的资源。

## 工程质量

以边界、正确性、可定位问题和可重复交付作为验收依据。新增依赖应说明用途；重要异常路径应有针对性验证；环境和运行步骤写入文档；实际进度附验证证据。公共模块改动需验证其消费者。
