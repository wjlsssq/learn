# 开发指南

## 协作分工

代码修改、静态自查和文档同步由代理负责，运行、构建和测试由用户负责。除非用户明确要求，代理不执行下文中的启动、构建、检查或测试命令，也不进行浏览器运行验证。

代理完成修改后按已有授权提交推送，并标注“未运行、未测试，由用户验证”，附建议验证的范围及必要命令。用户反馈结果后，再更新进度记录。下文命令保留供用户自行操作。

## 学习型代码与注释

所有工程均用于学习。按用户 2026-11-13 最新要求，后端新增和修改代码需充分、全面、面向新手的中文注释；前端无需新增注释。后端优先具名方法、显式循环和任务类，避免大量 Lambda；持久化使用原生 MyBatis，不使用 MyBatis-Plus。其余要求以 [AGENTS.md](../AGENTS.md) 为准。

- 文件、类和组件交代职责及调用关系，方法和函数解释输入、输出、异常与副作用。
- 关键逻辑按执行步骤说明，既解释当前操作，也解释设计原因、边界条件、失败处理和易错点。
- 新接触的注解、泛型、响应式、异步等概念先给通俗解释，再结合当前实现说明；变量及配置中的单位、默认值、可空性和修改影响写清楚。
- 公共代码说明如何接入、适合什么场景、有哪些限制；数据库和中间件接入后补充相应数据及可靠性约定。
- 严格 JSON 等文件的说明放在相邻文档中，保留可解析格式；生成文件和第三方代码保持原样。
- 每项新功能的开发文档给出建议阅读顺序和真实调用链。实现变更时同步更新注释，保持源代码、注释与文档一致。

## 环境准备

Docker 和 Compose 的原理、订单资源配置及观察实验见 [Docker 学习文档](../projects/order-lab/docs/DOCKER.md)。命令由用户自行执行，当前 Docker 仅运行订单中间件，门户与 Java 后端仍在宿主机启动。

订单工程的中间件、密码变量、迁移、独立启动和故障验收见[订单手册](../projects/order-lab/README.md)。前端入口 #projects/order-lab，后端端口 18081；Vite 将 /order-api 转发到订单后端。生产静态门户需要另配同路径反向代理。订单集成测试默认跳过，必须显式开启 ORDER_INTEGRATION_TESTS 并准备隔离的真实资源；代理未执行。基础服务仍使用原有 pnpm dev:backend。

| 工具    | 基线                  | 说明                                                           |
| ------- | --------------------- | -------------------------------------------------------------- |
| Git     | 支持 HTTPS 远端的版本 | 本仓库远端为 `https://github.com/wjlsssq/learn.git`            |
| Node.js | 22.12+ 的兼容版本     | 首次本地实现环境为 22.18；前端运行要求以根 `package.json` 为准 |
| pnpm    | 11.25.0               | 按根 `packageManager` 字段保持一致                             |
| JDK     | 17                    | `JAVA_HOME` 指向完整 JDK                                       |
| Maven   | Wrapper 固定 3.9.16   | 使用 `mvnw` / `mvnw.cmd`，无需依赖系统 Maven                   |

Windows PowerShell、Linux 和 macOS 均从仓库根目录运行命令。首次安装前端依赖、执行 Maven Wrapper 和解析 Java 依赖需要联网。代理、凭据等机器配置保留在本地，不写入源码。

检查环境：

```sh
git --version
node --version
pnpm --version
java -version
```

## 启动门户

```sh
pnpm install --frozen-lockfile
pnpm dev
```

默认访问 <http://127.0.0.1:5173>。基础服务尚未启动时，工程登记信息与文档仍可浏览。页面初始不假定服务在线，手动检查后才显示探测结果。

门户使用 Vite 开发代理：`/foundation-api/*` 转发到 `http://127.0.0.1:18080/*`。修改服务地址或端口时同步修改门户代理与工程登记信息，并更新文档。

## 工程页面与导航

点击文件夹后，右侧主内容区显示完整工程页，左侧菜单和顶部面包屑保留。工程说明、运行状态、能力、启动命令、学习目标、真实入口和关联文档均在工程页中展示，不再通过弹窗或抽屉打开。

门户使用 URL 片段（hash）标识页面，`#` 后面的内容由前端读取，不要求后端新增工程页路由：

| 地址 | 含义 |
| --- | --- |
| `http://127.0.0.1:5173/#projects` | 工程列表 |
| `http://127.0.0.1:5173/#projects/foundation-service` | 基础工程工作区 |
| `http://127.0.0.1:5173/#docs/development` | 开发指南 |

顶部面包屑可返回工程列表。复制工程页地址后重新打开或刷新，应仍显示同一工程；浏览器前进、后退应对应切换列表、工程和文档页。工程标识不存在时显示“找不到工程”页面，并提供返回列表的入口。

工程元数据由 `portal/src/projects.ts` 的 `ProjectDefinition` 和 `projects` 数组维护；`portal/src/navigation.ts` 负责解析和生成地址，`portal/src/App.vue` 根据解析结果查找当前工程。`portal/src/components/ProjectWorkspace.vue` 复用登记数据展示工程内容，新增工程无需重新编写基础工程信息展示。

建议阅读顺序：先看 `projects.ts` 的工程登记字段，再看 `navigation.ts` 如何解析地址，随后阅读 `App.vue` 如何查找工程及构造面包屑，最后阅读 `ProjectWorkspace.vue` 如何通过 `project`、`runtime`、`copyFeedback` 参数展示内容，并通过 `back`、`check`、`copy` 事件通知父组件处理操作。运行状态仍来自用户手动探测，地址切换不会启动本地服务。

本次导航修改的运行、构建、测试和浏览器检查均由用户负责。建议手动验收：点击文件夹进入完整页面、面包屑返回、直接访问并刷新工程地址、浏览器前进后退、未知工程提示，以及工程页中的入口、命令复制、服务状态和文档跳转。

## 排版与信息密度

工程网格卡片按用户最新要求等宽等高：grid-auto-rows: 1fr 配合拉伸对齐，正文使用弹性剩余空间，使底部分隔线和元信息对齐。高度随最长内容自然扩展，不截断正文；此规则针对工程目录卡片，详情页内容面板仍按内容自然取高。

工作台面向持续阅读与操作，正文、说明、命令和导航采用清楚的字号层级。字号、颜色等公共值集中在 `shared/frontend/ui/src/tokens.css`，全局页面布局在 `portal/src/style.css`，工程页布局在 `portal/src/project-workspace.css`。

字号使用 `rem`，即相对于浏览器根字号的单位。下表像素值按默认根字号 16px 换算，便于理解；用户改变默认字号时，实际显示尺寸也会随之变化。

| 内容角色 | 字号约定 | 用途 |
| --- | --- | --- |
| 辅助信息、标签和代码 | 0.875rem，约 14px | 元数据、状态说明、源码路径与命令 |
| 导航与操作 | 0.875rem 至 1rem，约 14–16px | 菜单、面包屑、按钮和表单控件 |
| 常规正文 | 1rem，约 16px；行高 1.65 | 工程说明、能力介绍、学习目标 |
| 长文阅读 | 1.125rem，约 18px | 仓库文档等连续阅读内容 |
| 面板标题 | 1.25rem，约 20px | 分组标题与内容层级 |
| 页面标题 | 2rem，约 32px；手机约 28px | 当前页面的主要标题 |

主要文字使用 `#18263e`，次要文字使用 `#42516a`，辅助文字使用 `#59677d`，品牌和主要操作使用 `#254cc5`。辅助信息仍需清楚可读，不通过很浅的灰色代替信息层级。以上字号与颜色是本项目的设计选择，不是 WCAG 指定值；对比度目标仍需结合真实前景、背景和状态由用户核对。

间距以 8px 为主要节奏，常用 8 / 16 / 24 / 32px，局部细节采用 4 / 12px。主区域使用完整可用宽度，内容内边距为 `clamp(1rem, 1.5vw, 1.75rem)`，即按视口变化、在默认根字号下保持约 16–28px；通过标题、面板、行距和对齐组织信息，减少原先顶部及两侧过大的空白。左侧菜单宽 16rem，视口到 56rem 及以下时收起，为正文保留空间。

列表页根据当前筛选结果数量分配列数：`App.vue` 在一个结果时添加 `single-project`，两个结果时添加 `two-projects`，由样式分别分配一列或两列；三个及以上结果最多三列。一个结果采用横向信息卡，不预留空工程槽位。视口到 80rem 及以下时最多两列，到 48rem 及以下时单列并恢复纵向卡片。大型接入占位块已移除，接入指南放在 `workspace-guide-actions` 普通操作行，不作为尚未建成的工程展示。

工程页将真实信息组织为三个独立内容组：操作组包含入口和命令，学习组包含能力和目标，参考组包含运行状态、源码位置和文档。视口达到 90rem 时三列，56rem 至 90rem 之间两列，56rem 及以下一列；两列时操作和学习依次排列在左侧，参考信息位于右侧。面板按内容自然增高，不强制等高拉伸，也不添加虚构功能或进度来填空白。

这里的 CSS Grid 用列和间距分配可用空间，响应式断点决定何时换列；窄屏时优先重排内容，而不是继续缩小文字。文档页使用约 18px 正文，面板最长 92ch；`ch` 是基于字体字符宽度的长度单位，限制长文行宽，不要求每行文字无限铺满屏幕。长 URL 与源码路径允许换行，命令保留完整内容并在自身区域处理横向滚动，避免把整个页面撑宽。整页工程导航、左侧菜单和顶部面包屑的规则保持不变。

阅读布局代码时，建议先看公共令牌的角色与默认值，再看全局容器和列表列数，最后看工程页的内容分组与断点。调整共享令牌后，需关注列表、工程页和文档页三个消费者。研究依据和设计取舍见 [ADR 0002](decisions/0002-readable-workspace-layout.md)。

运行检查由用户负责。建议在常用桌面宽度、窄窗口和手机宽度观察字号、内容分组与空白，再检查浏览器放大后的换行、长命令、面包屑、按钮和状态说明；必要时核对普通文字至少 4.5:1 的对比度目标，以及 320 CSSpx 宽度下的正文重排。未实际执行前，进度保持“已实现待用户验证”，不宣称已通过可访问性验收。

## 启动基础服务

另开终端，在仓库根目录执行：

```sh
pnpm dev:backend
```

脚本调用 Maven Wrapper 构建 `foundation-service` 及它的本地依赖，然后运行其可执行 JAR。开发启动构建跳过测试以缩短启动时间，完整验证由用户另行执行。

可以直接访问：

- <http://127.0.0.1:18080/api/foundation/info>
- <http://127.0.0.1:18080/actuator/health>

服务信息返回 `name`、`version`、`javaVersion` 和 `capabilities`。健康接口正常响应示例为 `{"status":"UP"}`。响应包含 `X-Request-Id`，用于关联日志与错误信息。

手动构建和启动的等价 Windows 命令：

```powershell
.\mvnw.cmd --batch-mode -pl projects/foundation-service -am package -DskipTests
java -jar projects/foundation-service/target/foundation-service-0.1.0-SNAPSHOT.jar
```

Linux / macOS 构建命令：

```sh
./mvnw --batch-mode -pl projects/foundation-service -am package -DskipTests
java -jar projects/foundation-service/target/foundation-service-0.1.0-SNAPSHOT.jar
```

在各自终端按 `Ctrl+C` 结束当前开发进程。Windows 后端开发脚本会清理其启动的进程树，不保证优雅关闭。结束验证时关闭自己启动的进程，保留用户原有进程。

## 检查与构建

```sh
pnpm check
pnpm check:backend
```

`pnpm check` 依次执行格式检查、ESLint、TypeScript 检查、测试和前端生产构建。`pnpm check:backend` 调用 Maven Wrapper 执行完整 Java `verify`。用户按改动影响范围选择检查，公共模块改动还应覆盖其实际消费者；代理提供范围说明，不执行检查。

其他常用命令：

| 命令                                    | 用途                            |
| --------------------------------------- | ------------------------------- |
| `pnpm format`                           | 格式化前端工具链管理的文件      |
| `pnpm build`                            | 生成门户静态产物 `portal/dist/` |
| `pnpm build:backend`                    | 构建 Java 工程                  |
| `pnpm --filter @learn/portal typecheck` | 仅检查门户类型                  |
| `pnpm --filter @learn/portal test`      | 运行门户测试                    |
| `pnpm --filter @learn/http test`        | 运行共享 HTTP 客户端测试        |
| `pnpm --filter @learn/portal preview`   | 预览静态生产产物，默认端口 4173 |

生产预览不等同于 Vite 开发服务。静态产物中的后端请求需要运行环境配置反向代理，未配置代理时不能据此判断基础服务本身存在故障。

Java 验证也可以直接执行：

```powershell
.\mvnw.cmd --batch-mode verify
```

Linux / macOS 使用 `./mvnw --batch-mode verify`。测试与构建报告位于各 Java 模块的 `target/` 中，不提交到 Git。

## 配置和依赖变更

直接依赖使用明确版本；变更前确认 Node、JDK、构建工具和相关插件的兼容性。前端依赖变更同步更新 `pnpm-lock.yaml`，干净环境采用 `--frozen-lockfile` 安装。

配置模板只包含安全示例。实际密钥、服务访问凭据和本地覆盖配置通过环境或忽略文件管理；浏览器可读取的配置不能承载私密凭据。

基础服务当前无数据库或中间件依赖。新增能力遵循 [PROJECT_ONBOARDING.md](PROJECT_ONBOARDING.md)，不将某个工程的依赖自动扩散到全部工程。

## 常见问题

| 现象                   | 检查步骤                                                                        |
| ---------------------- | ------------------------------------------------------------------------------- |
| 系统 Maven 太旧        | 使用仓库 Wrapper；通过 `mvnw.cmd --version` 或 `./mvnw --version` 核对          |
| Java 版本不符          | 核对 `java -version` 和 `JAVA_HOME`，确认 Wrapper 和终端使用同一 JDK            |
| 首次构建下载失败       | 检查网络与本地代理设置；修复后重试，不提交机器专用凭据或绕过失败项              |
| 门户显示未检测         | 点击检查服务状态，状态不会在首次渲染时被硬编码为在线                            |
| 门户探测失败           | 检查 18080 服务、直接健康接口和 Vite 代理；探测失败可能来自服务、网络或代理配置 |
| 5173 / 18080 被占用    | 确认占用进程归属；使用其他端口时同步更新相关配置与文档                          |
| 仅静态预览无法探测后端 | 确认运行环境是否提供 `/foundation-api` 反向代理                                 |
| 修改公共库后消费者失败 | 检查接口兼容性与消费者配置，补充对应回归验证                                    |

## 开发收尾

1. 检查差异与依赖边界，确认只修改本次范围。
2. 完成代码与差异的静态自查，说明建议验证的范围；标注运行和测试未执行，由用户验证。
3. 更新 [PROGRESS.md](PROGRESS.md)；影响运行、架构或接入步骤时同步对应文档。
4. 检查暂存内容，提交并推送 `origin main`，核对远端结果。

现有 GitHub Actions 仍对推送和拉取请求自动执行前端与 Java 检查。代理不主动触发或等待其运行；自动检查不替代用户验证，实际结果以对应提交为准。
